## 结局时钟、暂停与失败

游戏按 `12 秒`电影、之后字卡 `2 秒`控制，正常序列合计 `14 秒`；最终影片的实际时长和完整解码另由媒体审计确认。加载时间不消耗电影时间。暂停不推进字卡；媒体的实际解码进度与完整播放证明决定电影结束，单独一个接近结尾的时间值不能点灯。

视频损坏时从第 00 帧开始播放同剧情备用动画。当前目标帧确实成功显示才推进时钟；最近已载入的前帧可以留在画面上，但不能冒充当前帧。24 个目标帧均有成功证据后才进入字卡。缺帧会冻结，提供重新播放或无奖励返回，不把标题画面当成完整动画。

`secondGrade` 的生成电影之后，还有独立的私人录像序列：最多 10 秒录像，10–11 秒黑场，11–13 秒名言，13–15 秒谢幕；15 秒回廊。只有在截止前收到实际播放成功，才保存 `finalePlayed`。失败、无片、超时和旧回调不消耗首次私人录像的机会。

实际限制：浏览器和原生录像宿主保留自己的较长容错，但游戏层 10 秒截止控制这段序列。慢解码未能在截止前完成全部选中片段时，本次会保留重试状态；此逻辑检查不等于证明每台设备都能及时解码。

## 私人录像真实播放复验

`scripts/personal-finale-playback-check.cjs` 补充真正的录像播放证据，不再以播放层可见 450 毫秒代替三片完成。脚本复用 `browser-check.cjs` 为本次测试建立独占临时 Edge 资料目录，鼠标点出发、键盘实际跳跃，调用原有捕获入口录下三种真实活动画面，不注入 Blob。记录经 `MediaRecorder` 编码、IndexedDB 写入、整页重载后，三个 ID、类型、字节数和时长均保持一致。

Canvas 此次三片均为 `video/webm;codecs=vp8`：

| 类型 | 记录时长 | Blob 字节数 | 实际结束时媒体时间 | 结束时游戏时间 |
| --- | --- | --- | --- | --- |
| `highlight` | 3.100 秒 | 214896 | 3.067623 秒 | 3.233 秒 |
| `death` | 3.083 秒 | 209352 | 3.066643 秒 | 6.383 秒 |
| `hidden` | 3.033 秒 | 201730 | 3.000891 秒 | 9.467 秒 |

透明观察原播放器的三次起播、`playing`、`ended` 和实际回报，不制造成功回调。三个真实 `ended` 依次发生后，在游戏时间 `9.483333 秒` 收到成功，才将 `finalePlayed` 保存为 `true`。距离 10 秒截止仅剩约 `0.517 秒`，本结果说明本次宿主能按时完成，不能推广为所有设备的解码保证。

Escape 实际暂停约 1.1 秒，视频时间、游戏时间和终局画面时钟均冻结；鼠标点继续后正常播放。最终游戏时间 `15.000 秒` 返回回廊，含暂停的墙钟约 `16.729 秒`，读存档仍为 `true`，`secondGrade` 计数保持 `1`。首片、暂停、纯黑、名言、谢幕和回廊截图已亲眼复查。浏览器异常、控制台错误和网络错误均为空。

报告与截图在 `build/qa/personal-finale/canvas-report.json` 及同目录。脚本接受 URL，主验收可在最终 Cocos Web 包上另行运行：

```powershell
node scripts/personal-finale-playback-check.cjs 'http://127.0.0.1:4318/build/web-desktop/'
```

明确范围：录像捕获阶段为移除障碍的第一段安全样本，三个捕获类型通过真实捕获 API 标记，不证明对应事件自然触发；私人入口注入了四灯与已完成 `secondGrade` 的前置状态，并通过 `Game.startEnding('secondGrade',true)` / `finishEnding()` 跳过前一部生成电影的重看，隔离检查私人录像。测试没有修改 `phaseTime`、`currentTime`、更新速度或播放结果。失败、迟到与旧回调的证明继续由既有专项覆盖；本次仅证明桌面 Canvas 宿主成功路径，不声称 Cocos 或安卓真机已经通过。

## 安卓构建路径与最终打包资源审计

只读检查发现 `scripts/cocos-android.json` 的 SDK、NDK、Java 字段及旧生成工程的 `sdk.dir`、`RES_PATH`、`NATIVE_DIR`、`RELEASE_STORE_FILE` 仍指向 `E:\A Fleeting Life`；本机这些 E 盘 SDK/JDK 目录不存在，当前工作目录旁的 D 盘工具目录存在。旧脚本只设置环境变量，并没有覆写 Creator 的显式配置和 Gradle 的 `local.properties`，不能据此认定旧 E 盘配置已经被覆盖。

已修正 `build-cocos.ps1`：从已解析的 `FLEETING_TOOL_ROOT` 或项目上级寻找本机工具，仅在 Android 分支生成 `build/cocos-android-current.json`，Creator 使用该临时配置；源 JSON 不写入 D 盘个人路径。`prepare-android.cjs` 显式校正上述生成工程字段、`cfg.cmake` 与中文应用名，先验证 SDK、NDK、Java、引擎、原生目录和签名文件存在。生成的 Java properties 使用前斜线与标准转义。

主构建第一次实际运行被 AGP 的中文工程路径检查拒绝，原 `build/cocos-engine` 别名仍含中文，不能解决 Gradle 工程路径。追加修正后，每项 ASCII junction 的 realpath 与原始来源核对，`owner.json` 保存映射及所有者。Gradle 工作目录、缓存、RES/NATIVE、引擎、SDK/JDK 和签名文件均走 ASCII 路径，不使用 `android.overridePathCheck`。

之后发现把 Creator 也切到 junction 会产生缺失启动组件的实际候选：日志 `Missing class`、Main 的 `_components=[null]`、脚本没有 Bootstrap UUID 的 RF 注册。此候选虽然 native 编译成功仍不能交付，已由主构建归档到 `build/qa/android-rejected-startup-null-cf71e749.apk`。现已恢复 Creator 的原工程、可执行文件、配置与日志路径；ASCII 别名只用于最终原生编译。新的正式 Android 结果仍待主构建确认。

`node --test tests/android-build-paths.test.cjs tests/android-startup-artifacts.test.cjs` 7 项通过，包含真实 PowerShell 启动前代码（未启动 Creator）、实际 JDK 17 `Properties.load` 及 `File.getCanonicalPath()` 保持 ASCII、缺签名文件时写入前报错、未知或不匹配所有者的别名拒绝复用，以及非空挂载组件、UUID 注册、源 SHA 与实际 APK ZIP 字节验证。主构建另已将旧 E 盘 CMake 缓存的真实目录整体归档到 `build/android/pre-ascii-cache-20260929`，本补审只读确认归档存在且不是 junction。本补审未启动 Creator、Gradle 编译或 GPU。

原真实路径构建后，Main 组件恢复，但检查脚本误选共享 helpers 文件，造成一次假拒绝。已独立核对本机官方 Cocos `game.ts`、`jsb-loader.js` 与 `class.ts`：settings 预载 main，经 main config 的 `hasPreloadScript` 加载实际 `assets/main/index.js`，此入口内 RF frame UUID 会作为脚本 classId。当前 Android 14:54:09 已实际通过严格 guard，保留同一 UUID、非空组件、RF 注册和装饰器，不因平台跳过要求。

新构建脚本在 Creator 后强制产物 guard，在交付 APK 前强制完整 ZIP 中 settings、main config、Main 导入 JSON、main index 四项 SHA 和源指纹一致；失败报告覆盖旧通过证明且不复制到 `dist`。默认成功报告为 `build/qa/android-startup-artifacts.json` 与 `build/qa/android-startup-apk.json`，旧坏原生产物和正常 Web 参考的历史实测对照为 `build/qa/android-startup-rejected-current.json`。这项检查不冒充真机启动或原生视频实播。

已准备标准 Python 脚本 `scripts/audit-packaged-endings.py`。最终 28 条 `generation-manifest.json` 完成后才使用它验收新包：

```powershell
python scripts/audit-packaged-endings.py --web build/web-desktop --apk 'dist/浮生-第一章-debug.apk'
```

默认报告为 `build/qa/ending-films/packaged-resource-audit.json`，可用 `--out` 指定；`--manifest-dir` 可改为读取 28 条逐片记录。脚本严格要求七结局乘四服装的 28 条矩阵和 672 张源备用帧，验证当前源 SHA 仍与最终生成记录一致，再从 Web 实际文件和 APK ZIP 项按 `.meta` UUID 或资源路径逐片定位 MP4，对源和生成记录核 SHA。备用图要求实际原生图片文件存在，支持 Cocos 转换后的扩展名；不以 JSON 中声明过 UUID 代替实际文件，也不冒称转换图字节与源 PNG 相同。APK 直接流式读取 ZIP，不解包，并另记录整个 APK 的 SHA。

`python tests/packaged-ending-audit.test.py` 五项夹具测试通过：目录与 ZIP 的 28 片、672 图齐全；同 UUID 的旧 MP4 字节拒绝；只有元数据而没有实际图拒绝；生成后源被改拒绝；七条早审清单拒绝。这些是合成字节夹具验证脚本合同，不是当前旧包的最终验收。此阶段没有运行旧包资源审计，最终新包资源结果待主验收填写。即使该审计通过，也只证明资源已打包及影片字节一致，不能代替原生实播、运行时加载或真机性能证据。

本记录不声称“无 BUG”；最终电影文件、全部素材、整套回归及设备表现以主验收实际结果为准。
